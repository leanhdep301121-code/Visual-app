# 球描线 Tracer — Pipeline 技术报告

> 手机视频 → 球 2D 轨迹 → 3D 弹道 → carry / 球速 / 发射角。端上、纯单目、可解释。
> 更新：2026-07-16(重写。上一版 2026-07-09 的若干结论已被实测推翻,见 §5)

---

## 1. 数据流

```
视频
 │
 ├─ [S1] pose            yolo11n-pose (golf 蒸馏 swipose 320²) → 17 关键点/帧
 ├─ [S2] 事件分割        PoseTCN v3.1 → 8 事件(address…finish),给出 impact 帧
 ├─ [S3] 球 2D 检测      TrackNet(UNet 热力图) → 每帧所有 >0.5 的 blob
 ├─ [S4] 过滤            弹道链 + impact 门 + 平台剔除 → 球迹
 ├─ [S5] 几何            真内参(自录) / GeoCalib(imported) + 身体尺子 anchorZ
 ├─ [S6] 3D 拟合         BallFlightSolver 网格搜 → (speed, launch, azimuth, t0)
 └─ [S7] 投影/显示       俯仰重力投影 → 弧线 + 置信度 + carry
```

关键点:**impact 由 PoseTCN 给,不是猜的**。这是整条链上最干净的信号(实测夜间
softmax 0.97),S4 的核心过滤就靠它。

## 2. 过滤设计(S4)

这是整条链最容易出错的地方。TrackNet 用的是**羽毛球官方权重**(off-domain),
它对任何高速运动的光流都 fire —— 球、杆头、杆身拖影、背景杂物。

### 2.1 每帧留全部候选,不选最大面积
早期按「每帧最大面积 blob」选球,会选到杆头。改成保留所有 >0.5 的连通域,
交给下游的链去挑。

### 2.2 弹道贪心链
```
step = |Δpos| / Δframe < 0.14   → 可以接上
链长 >= 3 且 净位移 > 0.12       → 候选链
按 (净位移, 链长) 排序取第一     → 飞行球
```
静止球形成零位移链被剔;杆头孤点连不上被剔。

滑窗必须**按帧覆盖而非追加**:末窗为不丢帧会贴尾、与前窗重叠,追加会让重叠帧
凭空多出一倍候选,播下一堆平行假链去争冠军。对齐 `per_frame[s+f] = blobs(...)`。

### 2.3 impact 门 ★(2026-07-16 新增,今天最重要的修复)
**球在 impact 之前不可能在飞。** impact 前的半空点必然是杆(主要是**杆身拖影**,
不是杆头)。它们高度几乎不变 → vy≈0 → tee 反投除零。

实测 `314c3679`(1264×720 夜间):
| | 含杆身点 | 剔除后 |
|---|---|---|
| vy | -0.0017/帧 | -0.0764/帧 |
| back | **-83 帧** | -3.6 帧 |
| tee | **x = -7229 px** | x = 811 px(真球 802) |
| 引擎 | **拟合失败** | 39 m/s / 11° / carry 74m |

链里 impact 之前的点只有一种合法身份:**静止在地上的 address 球**(它和飞行段
是同一个物体,天然连续)。所以:
- **obs(拟合观测)只取 `t >= impact`**
- **tee**:链首若在 `groundY - 0.05` 以内 → 直接用链首(它就是 address 球);
  否则用**第一对 post-impact 点**反投到地平面

### 2.4 平台剔除
DTL 球往画面深处退时图像位移趋零,那些尾点**无 3D 信息却主导拟合**。
`thr = max(0.008·H, 0.35·median(step))`,连续 2 帧低于 thr 即截断,保留 >= 4 点。

### 2.5 退化护栏
`发射角 < 2° 或 > 44°`、`速度 >= 74 m/s`、`tee 反投出画面` → **不出 tracer**。
错线比没有更糟。

## 3. 物理弹道模型(S6/S7)

### 3.1 求解
有界网格搜 + 3 轮细化,4 个自由度:
```
speed  : 由 anchorZ 尺度定界
launch : 10…42°  步长 6
azimuth: -28…28° 步长 7      ← ±16 卡侧飞球;±40 放退化解;28 是甜点
t0     : -0.30…0  步长 0.075
```
**拟合用平地重力,只在投影时用俯仰重力**。把俯仰塞进拟合网格会把最小值推到慢解。

### 3.2 空气动力学 ★(2026-07-16 重做)
半隐式欧拉 @ 1/240,二次阻力 + Magnus 升力。
`kAir = ½ρA/m = 0.5·1.2·1.432e-3/0.0459`

**Cd 和 Cl 都按发射角(自旋代理)在实测锚点间线性插值:**
```
10.9° → Cd 0.21, Cl 0.16   PGA 驱杆 2686 rpm
16.3° → Cd 0.35, Cl 0.37   PGA 7铁  7100 rpm
20.0° → Cd 0.33, Cl 0.31   业余 7铁
```

基准复现:
| | Cd/Cl | carry | 顶高 | 滞空 |
|---|---|---|---|---|
| 驱杆 75m/s 10.9° | 0.21/0.16 | 260(真 256) | 31.2(真 32) | 6.6(真 6.4) |
| PGA 7铁 54m/s 16.3° | 0.35/0.37 | 158(真 158) | 32.1(真 32) | 6.5(真 6.3) |
| 业余 7铁 45m/s 20° | 0.33/0.31 | 128(真 130) | 21.5(真 22) | 5.2(真 5.0) |

**为什么不是调 g**:旧版 `Cd=0.25` 恒定 + `Cl` 挡位 0.18/0.22/0.27,球普遍
升不够 —— 顶高低 14–26%(7铁 23.8m vs 真实 32m),而 carry 只差 9%。
调小 g 能抬顶高,但会把**本已正确的 carry 一起抬飞**,拿一个错换另一个错;
而且 g 是这里唯一精确已知的量,一旦掺假,以后任何偏差都无法归因。
真因是 **Cd 被钉死**:自旋同时驱动 Cd 和 Cl,驱杆↔7铁自旋差 **2.6 倍**,
光靠 Cl 1.2 倍的跨度表达不了。

> ⚠️ 这些是**等效系数**,为让简化模型(无自旋衰减、无雷诺数依赖)复现真实弹道
> 而拟合,不是实测气动量。Cd 0.35 对真球偏高 —— 它在替模型没建的部分买单。

### 3.3 置信度与显示
```
err > 14/720·帧高  或 obs < 5 或 越界(20–80 m/s, 6–35°, 10–320m) → low
receding(平台剔除掉 >2 点)                                      → mid
否则                                                            → high
```
- **high/mid**:给**一个精确数字**(`39 m/s · 11° · 81 码`)。范围只是把不确定性
  甩给用户,他没法据此做任何决定。
- **low**:**不给数字**,只留 `弧形参考 · 距离未标定` + 轨迹。方向和弧形是几何,
  不吃尺度误差;球速和 carry 是同一个尺度误差的两种写法(carry≈v²),
  不能藏一个露一个。

> err 门限**必须按帧高缩放**。写死 14 是 720 高上的值,直接用在 1080×1920 上
> 严 2.7 倍,会让所有正常拟合判 low。这是分辨率隐含前提的典型坑。

## 4. 精度边界(诚实版)

> **不用杆头速度 / 球径 / device 传感器,单目绝对尺度被身体尺子锁死 ±20%。**

`anchorZ = fy × 1.62 / 躯干跨度` —— 假设人高 1.62m。±20% 来自**这个身高假设**,
不是来自焦距。**弧形和方向可靠,绝对尺度是估的。**

真锚只有三条:
1. **球径测深** —— address 球静止可见,直径精确已知 42.67mm,
   `depth = f × 0.04267 / 球像素直径`,**不用假设任何人的身高**。
   实测估算:上述 clip f=643、球约 7px → **~3.9m**,而身体尺子给 **2.4m**(差 1.6×,
   speed 会从 39 提到 60 出头,才是成年人全挥杆该有的区间)。
   **卡在 `GolfBallYOLO11n` 是假模型上**(见 §6)。
2. **杆头速度**(已知 2m 处 → smash → 球速)
3. **device 真内参 + IMU**

试过且**更差**的(别重走):pose 手当 tee(err 5.3→70px)、anchorZ 放网格搜
(err 2.4px 但 carry 过冲 167m)、地平面几何定 tee 深度(与身体尺子同源,没引入新信息)。

## 5. 2026-07-16 修掉的四个 bug(推翻旧结论)

上一版文档把**杆头检测器**列为「最大阻塞」。**这是错的。** 真正挡路的是四个
坐标/门控 bug,而且它们**都不报错,只是让结果悄悄变差**:

1. **TrackNet 不转向**(只咬竖屏)
   `detect(orientation:)` 收了参数**从没用过**,`decodeWindow` 读裸横帧
   (1920×1080)硬拉进 512×288。球坐标在**横帧**空间,下游(pose 踝、videoSize、
   overlay)全在**竖帧**空间。→ 「球的终点在天上」的字面成因:`y=0.137` 不是天,
   是没转正的横坐标。转正后链首 `(0.642, 0.696)` vs groundY `0.711` —— 它一直
   就是垫子上那颗球。

2. **没有 impact 门**(两边都有)→ §2.3

3. **GeoCalib 不转向 + 不保比**(横屏更致命)
   整帧硬拉进 320×576 竖框。竖屏源(0.5625 vs 0.5555)几乎无损所以一直没暴露;
   横屏源(1.76)横压 3.95× 纵拉 0.8×,**总畸变 4.9×** → `focal 302`(FOV 128°,
   手机不可能)→ `anchorZ 1.1m` → 尺度缩水 2.2× → 22 m/s。
   修:**中心裁剪到 320:576 再送**,焦距按裁剪后的垂直视场缩放。
   端上还叠加了不转向 —— 竖屏 clip 送进去是一张**又躺倒又压扁**的图,
   那行 `focal 1335 / pitch -26.2°` 看着像模像样,其实全是垃圾。

4. **err 门限带分辨率隐含前提** → §3.3

**杆头模型对这些一个都救不了。** 实测:污染点是**杆身拖影**,f24 时杆头在球那儿
`(800,650)`,污染点在 `(683,518)`,相距 0.15 归一化 —— 任何杆头 veto(阈值 0.05)
都够不着。而 impact 门需要的 impact,**PoseTCN 早就给了**。

修复效果(同一条 clip):
| | 修前 | 修后 |
|---|---|---|
| focal | 302 (FOV 128°) | **643** (FOV 88°) |
| anchorZ | 1.0m | **2.4m** |
| tee | **x = -7229 px** | **795 px**(真球 802) |
| 引擎 | **拟合失败** | **39 m/s / 11° / carry 74m** |
| err / 置信 | — | **14.0px / high** |

**共同教训**:这四个都是「PC 侧成立的隐含前提,搬到端上悄悄失效」——
cv2 自动转向、720 分辨率、竖屏输入。移植时抄的是代码,漏的是前提。

## 6. 已知阻塞:Models/ 里有假模型 ⚠️

```
ClubDetectYOLO11n.mlpackage  task=pose  names={0:'person'}  imgsz=[192,192]
GolfBallYOLO11n.mlpackage    task=pose  names={0:'person'}  imgsz=[192,192]
yolo11n-pose.mlpackage       task=pose  names={0:'golfer'}  imgsz=[320,320]  ← 真的
```
前两个 **`weight.bin` md5 完全相同**(`1cea8fad…`)—— 它俩是同一个文件,都是旧
COCO 192² pose 模型的副本。**杆头检测器和 YOLO 球检测器从来没在端上存在过。**

后果:Vision 拿 pose 模型的 raw multiArray 转 `[VNRecognizedObjectObservation]`
转不出来 → 每帧静默跳过 → `❌ no club track`。**1.36s 烧在假模型上,零产出,不报错。**
球的 YOLO 兜底通路(`VideoAnalyzer:212`)同理是死的 —— 我们以为有两层兜底,其实只有
TrackNet 一层。

成因:`.gitignore:20 Models/*` 把它们忽略了。commit `5e4a3dc`「杆模型上端」只提交了
**代码**,`.mlpackage` 一个字节都没进 git —— 真模型只存在于作者机器上。
**代码和权重走了两条路,只有代码那条有版本控制。**

**待办**:
- [ ] 找同事要 `GolfBallYOLO11n` 真权重(解锁球径测深 → 尺度)。杆头的可以先放着。
- [ ] `ClubDetectService.init` / `BallDetectService.init` 加 metadata 断言
      (`task=="detect"` && names 含目标类,不符直接 throw)。让假模型**响亮地死**,
      而不是静默返回零。

## 7. 下一步

### 7.1 球场实测 / 录 bag ★优先
现在整条链是**先单目估、再重建**,估的部分太多(焦距、俯仰、深度全在猜)。
tracing(2D 球迹)本身现在效果不错 —— 该往真值上靠的是物理那半截。需要去球场:

- **录 bag:视频 + 手机真 IMU(重力向量/姿态)同步落盘**。`CameraService` 已开
  `cameraIntrinsicMatrixDelivery` 并落盘 `camera_intrinsics_latest.json`,
  **自录杆的焦距是真的**,不用 GeoCalib 猜 —— 这条要在球场验通。
- 拿**真 IMU 重力**替掉 GeoCalib 的俯仰估计,直接检验物理引擎:
  已知发射条件下,预测弧 vs 实测弧的残差,才能把「引擎错」和「尺度错」分开。
  现在两者纠缠,任何调参都是在盲调。
- 覆盖:竖屏/横屏、白天/夜间、不同球杆(驱杆→短铁,拿自旋跨度检验 Cd/Cl 插值)。
- 有条件的话配一次测距/雷达真值,哪怕十几杆,用来标定 anchorZ。

### 7.2 物理弹道继续微调
Cd/Cl 插值现在只在**三个教科书基准**上对上了,球场真值一到就该重标锚点。
特别是 16.3°→20° 之间趋势反转(PGA 7铁自旋 > 业余 7铁,尽管发射角更低)——
说明**发射角当自旋代理有天花板**,长期看要么引入球杆选择,要么从球迹反解自旋。

### 7.3 Inference time ⚡
当前端上一条 clip **13.15s**(82 帧)。实测分解:
```
[perf] pose extraction (82 frames)          0.49s
[perf] events + metrics                     0.02s
[perf] club detect                          1.36s   ← 假模型,纯浪费
[perf] ball trajectory                      6.15s
        └ TrackNet: decode 1.00 | median 2.19 | infer 0.12 | heatdecode 1.46
[perf] geocalib + ball flight fit           5.13s
                                     total 13.15s
```
**ANE 推理本身只有 0.12s** —— 时间全花在推理以外。优化靶子很明确:

| 靶子 | 现状 | 方向 |
|---|---|---|
| club detect | 1.36s | **删掉/断言**(假模型,零产出) |
| TrackNet median | 2.19s | 中值背景抽 9 帧仍是 `[Float]` 数组循环 → vDSP/Accelerate |
| TrackNet heatdecode | 1.46s | 逐元素读 MLMultiArray + 边界检查 → 指针 + vDSP 阈值化 |
| TrackNet decode | 1.00s | 与 pose 共用一次解码,别各读各的 |
| geocalib + fit | 5.13s | 网格搜 4 DOF × 3 轮,可 SIMD 化 / 缩网格 |
| pose | 0.49s | 已经很快,不动 |

目标:**live 可跑**。注意上面是 DEBUG 构建,Release 约 20× 快,但 median /
heatdecode 这种纯数组循环仍是结构性开销,该改还得改。

## 9. 验证状态

**结论:2D 链路(检测 → 过滤 → tracer)端上实测通过,轨迹正确。唯一没解决的是
绝对距离 —— 那不是算法问题,是缺真值。**

| 改动 | 状态 |
|---|---|
| TrackNet 转向 | ✅ 端上实测,轨迹正确(这条是「球飞天上」的根因) |
| impact 门 | ✅ 端上 + PC 实测(overlay 人工确认) |
| GeoCalib 横屏裁剪 | ✅ PC 实测(focal 302→643, anchorZ 1.1→2.4) |
| 候选池按帧覆盖 | ✅ 随端上链路一起跑通 |
| 平台剔除 8→4 | ✅ 未见平/负发射角回归 |
| err 门限缩放 | ✅ 端上实测(修前所有杆误判 low →「距离未标定」) |
| 单数字显示 / 码 | ✅ 端上实测 |
| Cd/Cl 插值 | ⚠️ 仅三个教科书基准对上,**无球场真值** |
| **绝对距离/尺度** | ❌ **未解决** → §4、§7.1 |

### 现状定性
- **tracer 效果很好,轨迹很对** —— 方向、弧形、起点(address 球)都对得上。
- **距离数值不可信** —— `anchorZ` 靠身体尺子(假设人高 1.62m),±20% 是物理下限。
  这个数**调参调不出来**,必须实地采真值。

### 白天通路(尚未上端)
TrackNet 把 1080→512 缩图,3px 的球缩成亚像素直接没了。全分辨率 + 空间掩码 +
多候选 + 平滑抛物线选链 + 链内离群剔除 → swing_005 实测 14 点干净弹道(残差 0.0137)。
逻辑已验证,需 Swift 移植 + 掩码从固定框换 pose 框球员。
